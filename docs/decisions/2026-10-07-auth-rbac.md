# Accounts, roles and sessions (2026-10-07)

Requested and approved by Karan on 2026-10-07. This reverses the earlier scope line "No login, no admin role" in `PRD.md` §2 and §8 and in `CLAUDE.md`; both now point here. The five API capabilities (`configure`, `simulate`, `suitability`, `explain`, `chat`) are unchanged. The new routes are `/api/auth/*`, `/api/admin/*` and `/api/audit/*`.

## Decisions

| Topic             | Decision                                                                                                                                                                                                                                                                                                                                                                        |
| ----------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Roles             | **RM** (shown as "User"; the desk: simulate, suitability, explain, chat, plus their own saved runs) and **Admin** (everything an RM can do, plus every account's runs, the activity log and analytics, and user management). *Changed 2026-10-08 at Karan's request: the Compliance role was removed.*                                                                                                                                                             |
| Registration      | Public registration always creates an **RM**; the role is never read from the request. Admin accounts are created or promoted by an Admin. The first Admin is created from a trusted terminal: `ADMIN_EMAIL=… ADMIN_PASSWORD=… npm run seed:admin`.                                                                                                              |
| Login page        | *Changed 2026-10-08:* one page for everyone (no tab per role). The server decides the role from the account; the app then opens the simulator for a user and the admin console for an admin.                                                                                                                                                                                                |
| Passwords         | scrypt (N=65536, r=8, p=2, random 16-byte salt, stored as `scrypt$N$r$p$salt$hash`), compared in constant time. 10–128 characters with a lowercase letter, an uppercase letter and a digit. Wrong-password, unknown-email and deactivated-account answers are identical and take similar time. Five failed attempts per address and email lock further attempts for 15 minutes. |
| Tokens            | Own implementation on Supabase (chosen over Supabase Auth to keep the repository abstraction): a stateless HS256 **access token** (15 min) and an opaque random **refresh token** (7 days) that is stored only as a SHA-256 hash and **rotated on every use**. Replaying a rotated token after a 10 s grace window revokes the whole session family.                            |
| Cookies           | `ms_access` (httpOnly, SameSite=Strict, path `/api`), `ms_refresh` (httpOnly, SameSite=Strict, path `/api/auth`), both `Secure` in production; `ms_theme` (readable by script, SameSite=Lax) holds the dark-mode setting.                                                                                                                                                       |
| Settings          | Stored per user on the server (`app_users.settings`): `theme` (`light`, `dark`, `system`) and `customCursor`. The theme is mirrored in `ms_theme` and applied before first paint.                                                                                                                                                                                               |
| Payload hashing   | The web client sends `X-Payload-Hash`, the hex SHA-256 of the exact request body bytes, with every request that has a body. The API verifies it against the raw bytes (`400 PAYLOAD_HASH_MISMATCH`) and requires it when `PAYLOAD_HASH_REQUIRED` is true (default in production). It is an **integrity check, not authentication**: anyone who can call the API can compute it. |
| Enforcement       | `AUTH_ENFORCED` defaults to true in production and false elsewhere. When false, anonymous requests may use the simulator (so development and the existing tests work without a database); the admin and audit routes always need a sign-in, and a signed-in user is always held to their role. `AUTH_JWT_SECRET` (32+ characters) is required in production.                    |
| Live price socket | `/api/live` checks the access cookie on the WebSocket upgrade when sign-in is enforced.                                                                                                                                                                                                                                                                                         |
| Audit view        | `GET /api/audit/simulations` lists recent persisted simulations (read-only, Admin). *2026-10-08:* each run is now linked to the account that ran it (`simulations.user_id`), a user lists only their own (`GET /api/runs`), and the admin console adds analytics and an activity log (see `API_SPEC.md`).                                                                                                                                                                                                                                   |

## Known limits (not decided; flag if they matter)

- A role change or deactivation ends refresh tokens at once, but an already issued access token stays valid until it expires (at most `AUTH_ACCESS_TTL_SECONDS`, default 15 minutes).
- Runs saved before the 2026-10-08 migration have no owner (`user_id` is null): they show in the admin's list as "No account" and in nobody's own list.
- The login throttle is in memory and per process (no Redis, per `CLAUDE.md`). Behind a reverse proxy, set Express `trust proxy`, otherwise every client shares the proxy's address.
- Public registration is open once `AUTH_ENFORCED` is on: anyone who can reach the API can create an RM account. Restrict it at the network edge, or ask for a registration switch.
- Scrypt runs on the libuv thread pool, so a flood of sign-ins can slow other work on that process.
